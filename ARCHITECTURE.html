Topology and every path a packet may take

How frp reaches a private instance — and what it costs

Per-player instances are created with no published ports and a dnsrr endpoint: nothing on the challenge host listens for the player. The only way in is an frp tunnel, and understanding its direction is the whole security argument.

What frp costs, honestly

frp is a hole-punching proxy. Its purpose is to make something reachable that the network was arranged not to reach, so adopting it necessarily gives back some of the isolation the rest of this design buys. Five specific costs, and what each is worth:

CostWhy it is realWhat holds it down here
frpc bridges two zones It sits on the challenge overlay and the CTFd internal network. Isolation between them is now enforced by an application proxy, not by the kernel. A compromised frpc can reach any container on the overlay, on any port. frpc runs no player code and parses only frp's own protocol. It is the single most security-relevant process in the deployment.
Its config is rewritable over HTTP Whale drives frpc with PUT /api/config — whoever reaches frpc:7400 with the credential can rewrite every proxy rule, including ones pointing at internal addresses. Whale's own docs warn against binding this to 0.0.0.0. Bound to an internal Docker network with no host port, behind basic auth with a generated 32-char password. Not reachable from the VPN or the internet.
Hostile traffic now lands on the public node Before whale, every packet a player aimed at a challenge terminated on the isolated challenge host. Now instance traffic terminates on the node that also runs the scoreboard, its database and the Swarm manager. frps only relays; the exploitable service still runs on the challenge host. But the blast radius of an frps bug is the public node.
Pinned to frp 0.42.0 (2022) Whale speaks the INI-era admin API; frp ≥ 0.52 moved to TOML and is incompatible. So this is a four-year-old network daemon that will receive no security fixes. Reachable only from inside the VPC. Accepted deliberately — but it is the strongest argument for tearing the range down between events.
Players can reach each other's instances — closed The gateway allows the whole player range to the whole instance port range, and ports are sequential and guessable. A player can scan 10.0.0.3:10000-10100 and connect to someone else's private instance. Closed. The gateway now allows only (source address . port) pairs belonging to the player's own team, reconciled from CTFd every few seconds; everything else in the range hits a counted drop.

On that last row. This was the one isolation gap whale introduced, and it is now closed. Three systems each hold a third of the answer and share a database: whale knows user → port, the VPN-handout plugin knows user → VPN address (recorded for attribution), and CTFd knows user → team. The plugin joins them behind a token-guarded endpoint; a poller on the gateway turns the result into an nftables set keyed on ipv4_addr . inet_service. Teammates share an instance, other teams are dropped. It needs CTFd in teams mode — a setup-time, irreversible choice — and degrades to per-player isolation automatically in users mode.

Four layers, in the order a packet meets them

1 · Cloud Firewall

Outside the instance, attached at creation. Inbound DROP; only 1194/udp, 80/443 and operator SSH are punched through. Still holds if a compromised host flushes its own rules.

2 · Host nftables

Gateway: full forward DROP policy — player/admin ACLs, VPN↔VPN drop, metadata drop. Docker hosts: a separate ctf_guard table ahead of Docker’s chains that only adds denials, never flushes.

3 · Swarm stack / whale

Static: mode=host, worker-only, cap_drop ALL, read-only, limits, flag as a secret. Dynamic: whale via a socket proxy, no published ports, unique flag per instance, 60-min reaper, one live instance per player.

4 · OpenVPN

ccd-exclusive: a certificate without a static-IP entry is refused. Per-account profiles, CRL + management-socket kill for revocation, CN↔IP shipped to Wazuh for attribution.
